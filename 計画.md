SideStore Tailscale Reflector — Single Binary 実装仕様

1. 目的

SideStore 0.6.3+ の新しい minimuxer を、iPhone の Tailscale VPN を切断せずに利用できるようにする。

既存の shiqi917/sidestore-vpn-tailscale が必要としている以下をすべて廃止する。

Docker
tailscaled 外部プロセス
/dev/net/tun
NET_ADMIN
iptables / nftables
Linux network namespace
Rust reflector

最終成果物は、

sidestore-reflector

という 単一 Go バイナリ・単一プロセスにする。

必要なのは、

通常ユーザー権限
永続 state directory
Tailnet への通信

だけとする。

⸻

2. 前提となる SideStore の挙動

新しい SideStore/minimuxer は VPN interface が

device IP = A

なら、接続先を

A + 1

として扱う。

例:

iPhone Tailscale IP
100.101.102.103
SideStore が接続する peer
100.101.102.104

したがって reflector 自身の Tailscale IPv4 を必ず

NODE_ADDR = DEVICE_ADDR + 1

にする。

既存実装もこの方式を採用している。 (GitHub)

Tailscale の CGNAT range に subnet route を広告する方式ではなく、

reflector node 自身の Tailscale IP

を DEVICE_ADDR + 1 に設定する必要がある。

⸻

3. パケットフロー

例えば SideStore がローカルの RSD service の port Q に接続しようとする場合、

iPhone:P
   ↓
NODE_ADDR:Q

という packet を Tailscale に送る。

reflector はこの packet を受けて、

src = iPhone
dst = NODE_ADDR

を、

src = NODE_ADDR
dst = iPhone

にする。

port は変更しない。

したがって:

DEVICE:P → NODE:Q
           ↓ reflect
NODE:P → DEVICE:Q

となる。

これによって iPhone 上の port Q に packet が到達する。

サービスからの応答は、

DEVICE:Q → NODE:P

なので、もう一度 reflector を通ると、

NODE:Q → DEVICE:P

になる。

結果として最初の client socket P に response が戻る。

全体:

SideStore/client :P
        │
        │ DEVICE:P → NODE:Q
        ▼
   Tailscale VPN
        │
        ▼
┌───────────────────────────┐
│ sidestore-reflector       │
│                           │
│  WireGuard decrypt        │
│       ↓                   │
│  tun.Device.Write()       │
│       ↓                   │
│  swap IPv4 src/dst        │
│       ↓                   │
│  in-memory queue          │
│       ↓                   │
│  tun.Device.Read()        │
│       ↓                   │
│  WireGuard encrypt        │
└───────────────────────────┘
        │
        │ NODE:P → DEVICE:Q
        ▼
 iPhone local service :Q
        │
        │ DEVICE:Q → NODE:P
        ▼
   reflector again
        │
        ▼
 NODE:Q → DEVICE:P
        │
        ▼
 SideStore/client :P

既存 Rust reflector も transport header や port には触れず、IPv4 src/dst のみ交換している。 (GitHub)

⸻

4. tsnet を使う理由

tsnet.Server は Tailscale node を Go process 内に直接組み込める。

外部の

tailscaled
tailscale0

は不要。

現在の tagged version tailscale.com v1.102.3 では、

type Server struct {
    ...
    Tun tun.Device
}

が公開されている。 (Go Packages)

Tailscale 内部ではこの custom device が

wgengine.Config{
    Tun: s.Tun,
}

として userspace WireGuard engine に渡される。

custom TUN 指定時は通常の tsnet fake TUN ではなく、packet をその device に流す実装になっている。 (GitHub)

したがって、

WireGuard → custom tun → reflector → custom tun → WireGuard

を完全にメモリ内で実現できる。

7. custom tun.Device

使用する interface は Tailscale の fork:

import "github.com/tailscale/wireguard-go/tun"

概念上必要なメソッドは、

type Device interface {
    File() *os.File
    Read(bufs [][]byte, sizes []int, offset int) (int, error)
    Write(bufs [][]byte, offset int) (int, error)
    MTU() (int, error)
    Name() (string, error)
    Events() <-chan Event
    Close() error
    BatchSize() int
}

である。WireGuard の TUN interface はこの形になっている。 (ZX2C4 Git Repository)

重要なのは方向。

Write()
    Tailscale/WireGuard から復号されて
    「OS側へ出そうとしている packet」
Read()
    OS/TUN 側から WireGuard に渡して
    Tailnet へ送信する packet

したがって reflector は、

Write()
  ↓
swap
  ↓
queue
  ↓
Read()

でよい。

8. ReflectTun の構造

type Device struct {
    deviceIP netip.Addr
    nodeIP   netip.Addr
    rx chan []byte
    events chan tun.Event
    done   chan struct{}
    closeOnce sync.Once
    reflected atomic.Uint64
    dropped   atomic.Uint64
}

rx は例えば

make(chan []byte, 256)

とする。

SideStore の通信量であれば十分。

最初は batching を実装せず、

BatchSize() int {
    return 1
}

にする。

これは性能より correctness を優先するため。

9. Device constructor

func New(deviceIP, nodeIP netip.Addr) *Device {
    d := &Device{
        deviceIP: deviceIP,
        nodeIP:   nodeIP,
        rx:       make(chan []byte, 256),
        events:   make(chan tun.Event, 1),
        done:     make(chan struct{}),
    }
    d.events <- tun.EventUp
    return d
}

EventUp は buffered channel に最初から投入しておけばよい。

Tailscale 自身も WireGuard device を明示的に Up() するため、これが WireGuard startup の主体ではないが、TUN interface の状態として正しい情報を返しておく。 (GitHub)

11. IPv4 reflector

MVP では IPv4 のみ扱う。

さらに既存 implementation より条件を厳しくして、

src == configured iPhone IP
dst == reflector node IP

の packet だけ reflect する。

これによって別の Tailnet peer が reflector を悪用できる範囲を減らせる。

実装:

func reflectIPv4(
    pkt []byte,
    deviceIP netip.Addr,
    nodeIP netip.Addr,
) ([]byte, bool) {
    if len(pkt) < 20 {
        return nil, false
    }
    if pkt[0]>>4 != 4 {
        return nil, false
    }
    ihl := int(pkt[0]&0x0f) * 4
    if ihl < 20 || ihl > len(pkt) {
        return nil, false
    }
    totalLen := int(binary.BigEndian.Uint16(pkt[2:4]))
    if totalLen < ihl || totalLen > len(pkt) {
        return nil, false
    }
    src := netip.AddrFrom4([4]byte{
        pkt[12], pkt[13], pkt[14], pkt[15],
    })
    dst := netip.AddrFrom4([4]byte{
        pkt[16], pkt[17], pkt[18], pkt[19],
    })
    if src != deviceIP || dst != nodeIP {
        return nil, false
    }
    var tmp [4]byte
    copy(tmp[:], pkt[12:16])
    copy(pkt[12:16], pkt[16:20])
    copy(pkt[16:20], tmp[:])
    return pkt[:totalLen], true
}

checksum について

src/dst の 交換だけなら checksum の再計算は不要。

IPv4 header checksum は source/destination address の各 16-bit word の one’s-complement sum を含む。

src words + dst words

を

dst words + src words

にしても和は同じ。

TCP/UDP pseudo-header も同様に

source IP + destination IP

を含むため、swap のみなら checksum は変化しない。

port や payload も変更しない。

したがって byte-level swap だけでよい。

12. Write()

Write() は WireGuard から復号済み packet が入ってくる入口。

func (d *Device) Write(bufs [][]byte, offset int) (int, error) {
    written := 0
    for _, buf := range bufs {
        if offset < 0 || offset > len(buf) {
            return written, io.ErrShortBuffer
        }
        pkt := append([]byte(nil), buf[offset:]...)
        pkt, ok := reflectIPv4(
            pkt,
            d.deviceIP,
            d.nodeIP,
        )
        if !ok {
            d.dropped.Add(1)
            written++
            continue
        }
        select {
        case d.rx <- pkt:
            d.reflected.Add(1)
            written++
        case <-d.done:
            return written, os.ErrClosed
        }
    }
    return written, nil
}

必ず packet をコピーする。

Tailscale/WireGuard 側が渡した buffer の ownership を保持できる保証はないため、

append([]byte(nil), ...)

で独立させる。

⸻

13. Read()

WireGuard が Tailnet へ送る packet を要求する側。

func (d *Device) Read(
    bufs [][]byte,
    sizes []int,
    offset int,
) (int, error) {
    if len(bufs) == 0 || len(sizes) == 0 {
        return 0, io.ErrShortBuffer
    }
    select {
    case <-d.done:
        return 0, os.ErrClosed
    case pkt := <-d.rx:
        if offset < 0 || offset+len(pkt) > len(bufs[0]) {
            return 0, io.ErrShortBuffer
        }
        copy(bufs[0][offset:], pkt)
        sizes[0] = len(pkt)
        return 1, nil
    }
}

WireGuard はここで得た packet の destination Tailscale IP を見て適切な peer に暗号化して送信する。

reflection 後は、

src = NODE_ADDR
dst = DEVICE_ADDR

なので iPhone peer に戻る。

⸻

14. Close()

rx channel 自体は close しない。

Write() と競合すると send-on-closed-channel panic が起こり得るため。

func (d *Device) Close() error {
    d.closeOnce.Do(func() {
        close(d.done)
        close(d.events)
    })
    return nil
}

Read / Write は done を監視する。

17. reflector node IP を必ず検証する

これは非常に重要。

tsnet client 自身から任意の Tailscale IPv4 を選択することはできない。

最初の enrollment 時には control plane が通常の IP を割り当てる。

したがって Up() 後、

status.TailscaleIPs

から IPv4 を取り出し、

actual == DEVICE_ADDR + 1

か検証する。

例えば:

func findIPv4(addrs []netip.Addr) (netip.Addr, bool) {
    for _, addr := range addrs {
        if addr.Is4() {
            return addr, true
        }
    }
    return netip.Addr{}, false
}

そして、

actual, ok := findIPv4(status.TailscaleIPs)
if !ok {
    log.Fatal("tsnet node has no Tailscale IPv4")
}
if actual != nodeIP {
    log.Fatalf(`
reflector has wrong Tailscale IPv4.
iPhone:
    %s
Required reflector IP:
    %s
Current reflector IP:
    %s
Open Tailscale Admin Console,
edit this machine's IPv4 address to %s,
then restart sidestore-reflector.
`,
        deviceIP,
        nodeIP,
        actual,
        nodeIP,
    )
}

IP mismatch の状態で packet forwarding を開始しない。

21. security

既存 reflector は、

dst == reflector address

なら基本的に reflect する。

新実装ではさらに

src == configured device IP

を要求する。

つまり、

if src != iPhone {
    drop
}

とする。

さらに以下を禁止する。

IPv6
non-Tailscale source
wrong destination
malformed IPv4

MVP ではこれらを silent drop し、counter だけ増やす。

packet 単位の logging はしない。

SideStore refresh 中は packet 数が多くなるためログが過剰になる。

28. 注意すべき Tailscale の挙動

custom Tun を設定すると tsnet は通常の fake TUN ではなく、その device へ packet を流す。

一方で tsnet 自身の Listen() 等で登録された local transport endpoint は gVisor netstack が処理できるようになっている。現在の実装では custom TUN 時に、

CheckLocalTransportEndpoints = true

となっている。 (GitHub)

そのため reflector process 自体では不要な

srv.Listen(...)
srv.ListenPacket(...)

を作らない。

reflector の packet を gVisor listener に奪われる可能性を減らす。

⸻

29. IPv6

MVP は IPv4 only とする。

理由:

既存 sidestore-vpn-tailscale の仕組みが
Tailscale IPv4 + 1 を前提としている

ため。

IPv6 packet は明示的に drop。

将来 SideStore/minimuxer が IPv6 peer derivation を使用するようになった場合のみ別途実装する。

IPv4/IPv6 を曖昧に同時対応しない。

⸻

30. node IP collision

DEVICE_ADDR + 1 がすでに別 Tailnet node に使われていた場合、任意の別 address に変更してはいけない。

SideStore 自身が +1 を接続先にするためである。

その場合は、

1. DEVICE_ADDR を別の空きアドレスへ変更
2. DEVICE_ADDR + 1 も空いていることを確認
3. reflector をその +1 に設定

する。

startup 時には最低でも

actual reflector IP == computed nodeIP

を必須チェックする。

⸻

31. 複数 iPhone

Tailscale/tsnet は 1 process 内に複数の独立した Server を持てる。公式 documentation でも server ごとに異なる Dir と Hostname を使う方式が示されている。 (GitHub)

したがって将来的には、

devices:
  - name: iphone
    ip: 100.101.102.103
  - name: ipad
    ip: 100.105.20.30

から、

tsnet node #1 = 100.101.102.104
tsnet node #2 = 100.105.20.31

を 同じ executable / process 内で起動できる。

ただし MVP では実装しない。

まず 1 device = 1 tsnet.Server に限定する。

34. やらない方がよい実装

以下は避ける。

exec.Command("tailscaled")
exec.Command("iptables")
exec.Command("ip")
/dev/net/tun の作成
network namespace の作成
embedded shell script
Docker fallback

それらを入れると single-binary 化の利点が消える。

また Go binary の中に tailscaled executable を embed.FS で埋め込んで展開する方法も採用しない。

これは「1ファイル配布」ではあっても、

1 process
no system networking configuration

ではないため。

今回の設計では Tailscale networking stack 自体を library として直接組み込む。
